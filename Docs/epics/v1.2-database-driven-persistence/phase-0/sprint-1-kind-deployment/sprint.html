Sprint 1: kind Deployment & Persistence

Phase: 0 Sprint: 1 Depends on: Sprint 0 (SQLite API Container)

Objective

Deploy the SQLite API container to a local kind cluster with persistent storage. Create the kind cluster config with extraPortMappings for NodePort access and extraMounts to persist the database file on the Mac host filesystem. Write all Kubernetes manifests (Namespace, PersistentVolume, PersistentVolumeClaim, Deployment, Service) and verify the full stack is reachable at localhost:30080.

Rationale & Context

kind runs a Kubernetes control plane and worker nodes inside Docker containers. By default, any data stored inside a kind pod is ephemeral — it vanishes when the pod restarts or the cluster is deleted. To persist the SQLite database across restarts, we need a PersistentVolume backed by the Mac host filesystem.

The kind extraMounts configuration maps a host directory (./data/) into the kind node container at /kind-host-data. A hostPath PersistentVolume then mounts this path. The Deployment references a PersistentVolumeClaim which binds to this PV. This ensures the job-search.db file lives at ./data/job-search.db on the Mac and survives cluster teardown, image rebuilds, and pod restarts.

The NodePort service maps port 30080 on the kind node (and thus on the Mac host, via extraPortMappings) to port 8000 inside the pod. This makes the API accessible at http://localhost:30080 from any process on the Mac.

Existing kind (v0.31.0) and kubectl are installed but no kind clusters are running. Kubectl is currently pointed at a work EKS cluster — the kind config will need to be used with explicit --kubeconfig or the kind context will be switched.

Execution Plan

1. Write kind Cluster Config

  1. Task 1.1: Write kind-config.yaml 
    kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
  extraPortMappings:
  - containerPort: 30080
    hostPort: 30080
    protocol: TCP
  extraMounts:
  - hostPath: ./data
    containerPath: /kind-host-data

    Note: hostPath is relative to the directory where kind create cluster is run. The script will run from the repo root so ./data/ resolves correctly.

2. Write Kubernetes Manifests

  1. Task 1.2: Write namespace.yaml 
    apiVersion: v1
kind: Namespace
metadata:
  name: job-search
  2. Task 1.3: Write pv.yaml and pvc.yaml

    PV: 1Gi, hostPath /kind-host-data, ReadWriteOnce, no storage class (static provisioning). PVC: 1Gi, ReadWriteOnce, binds to the PV by name (volumeName: job-search-db-pv), in job-search namespace.

  3. Task 1.4: Write deployment.yaml

    Key specs:

    • 1 replica, app: sqlite-api label
    • Image: job-search-db:latest (loaded into kind via kind load docker-image)
    • imagePullPolicy: IfNotPresent (never pull from registry)
    • Volume mount: name: db-storage, mountPath: /data
    • Env: DB_PATH=/data/job-search.db
    • Readiness probe: httpGet on /health port 8000, initial delay 5s, period 10s
    • Resources: requests 64Mi memory, 100m CPU; limits 256Mi memory, 500m CPU
  4. Task 1.5: Write service.yaml

    ClusterIP on port 8000 + NodePort on 30080. Selector: app: sqlite-api.

3. Create Startup Script

  1. Task 1.6: Write start-cluster.sh

    Convenience script that:

    1. Checks if kind cluster job-search-local exists; if not, creates it with kind create cluster --config k8s/kind-config.yaml --name job-search-local
    2. Builds the Docker image: docker build -t job-search-db:latest db/
    3. Loads the image into kind: kind load docker-image job-search-db:latest --name job-search-local
    4. Applies all manifests: kubectl apply -f k8s/namespace.yaml -f k8s/pv.yaml -f k8s/pvc.yaml -f k8s/deployment.yaml -f k8s/service.yaml
    5. Waits for the deployment to be ready: kubectl rollout status deployment/sqlite-api -n job-search --timeout=60s
    6. Prints: API ready at http://localhost:30080 — verify with: python3 db/client.py health

4. Deploy and Verify

  1. Task 1.7: Create kind cluster and apply manifests

    Run bash db/start-cluster.sh. Verify output shows all resources created and deployment rolled out.

  2. Task 1.8: Verify API is reachable and DB persists
    • python3 db/client.py health → {"status": "ok"}
    • python3 db/client.py stats → {"total_jobs": 0} (empty, migration hasn't run yet)
    • Insert a test job: python3 db/client.py jobs insert '{"url":"https://test/j/1","title":"Persistence Test","company":"TestCo","first_seen":"2026-06-09T00:00:00Z","last_updated":"2026-06-09T00:00:00Z","dedup_key":"testco_persistence-test"}'
    • Verify: ls -la data/job-search.db shows the file on the Mac host
    • Simulate pod restart: kubectl delete pod -l app=sqlite-api -n job-search
    • Wait for new pod: kubectl rollout status deployment/sqlite-api -n job-search
    • Verify data survived: python3 db/client.py jobs list still shows the test job
    • Clean up test data: python3 db/client.py jobs update 1 --status skipped

Verification & Acceptance Criteria

  • kind create cluster --config k8s/kind-config.yaml --name job-search-local succeeds and kind get clusters shows job-search-local
  • All k8s manifests apply without errors: namespace, PV, PVC, deployment, service
  • kubectl get pods -n job-search shows sqlite-api pod with status Running and readiness probe passing
  • curl http://localhost:30080/health returns {"status": "ok"}
  • python3 db/client.py health works without specifying --api-url (uses default localhost:30080)
  • python3 db/client.py stats returns valid aggregate counts (0 jobs initially)
  • After inserting a job and deleting the pod, the job is still queryable (data persists)
  • ls data/job-search.db shows the SQLite file on the Mac host filesystem
  • bash db/start-cluster.sh is idempotent: running it when the cluster already exists skips creation and just ensures manifests are applied
  • Port 30080 does not conflict with any existing services on the host
