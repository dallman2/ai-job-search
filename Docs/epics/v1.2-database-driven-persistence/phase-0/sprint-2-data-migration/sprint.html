Sprint 2: Data Migration

Phase: 0 Sprint: 2 Depends on: Sprint 1 (kind Deployment & Persistence)

Objective

Write and execute a migration script that reads all 71 jobs from job_scraper/seen_jobs.json, imports them into the SQLite database via the API, and migrates the scrape run history. Verify data integrity with row counts, field-level spot checks, and a diff against the source JSON. After verification, archive the JSON and CSV files as .bak (not deleted).

Rationale & Context

The current seen_jobs.json contains 71 job entries with 10 fields each, plus a run_history array with scrape run metadata. The migration must handle the known data quality issues: 22 entries missing the source field, 18 entries with empty company strings, and truncated description fields (300–500 chars) where the full markdown was not stored.

The migration is additive: it inserts into the database without modifying the source files. After successful verification, the JSON and CSV files are renamed to .bak and the database becomes the source of truth. Phase 1 will then update all skill files to read from the DB instead.

The dedup_key in the database is auto-generated by the API during POST /jobs. The migration script sends the raw fields; the API constructs the key from normalized company+title. This ensures all future inserts (both migration and new scrapes) use the same key construction logic.

Execution Plan

1. Write the Migration Script

  1. Task 2.1: Write migrate.py

    Script structure:

    1. Load job_scraper/seen_jobs.json
    2. Parse seen dict and run_history array
    3. For each job entry, construct a JSON payload mapping the old field names to the new schema:
      • title → title
      • company → company (default "" if missing)
      • url → url
      • source → source (omit if not present)
      • location → location (default "" if missing)
      • salary → salary (omit if empty)
      • description → description_md AND description_text (strip markdown syntax for text)
      • fit_rating → fit_rating (map to valid enum: high/medium/low/unrated; default "unrated")
      • status → status (all are currently "new")
      • first_seen → first_seen
      • last_updated → auto-set by API
      • dedup_key → auto-generated by API from company+title
    4. POST each job to /jobs. Track successes and failures (duplicate URLs should not occur — all 71 URLs are unique — but handle gracefully).
    5. For each entry in run_history, POST to /scrape-runs.
    6. Print migration report: Migrated X jobs successfully, Y failures, Z scrape runs.
    7. Verify: GET /stats and confirm total_jobs == 71.
    8. Print per-status and per-fit_rating breakdowns for visual confirmation.

2. Migrate Description Fields

  1. Task 2.2: Handle description_md / description_text transformation

    The current description field contains truncated markdown (300–500 chars). During migration:

    • description_md gets the raw markdown as-is from the JSON
    • description_text is a plaintext version for FTS5 indexing: strip markdown syntax (headings #, bold **, links [](), code fences) using simple regex replacements
    • Future scrapes will store the full browser_markdown output (not truncated) in description_md

3. Execute Migration

  1. Task 2.3: Run migration against the live database

    python3 db/migrate.py --api-url http://localhost:30080

    Expected output: Migrated 71 jobs successfully, 0 failures, N scrape runs.

  2. Task 2.4: Verify data integrity
    • python3 db/client.py stats → total_jobs = 71
    • python3 db/client.py jobs list --status new --limit 1 → spot-check one entry: verify title, company, URL match the source JSON
    • python3 db/client.py jobs get 1 → verify all fields populated correctly
    • python3 db/client.py jobs search --q "kubernetes" → verify FTS5 returns relevant results
    • Compare source JSON count (71) with DB count: python3 -c "import json; print(len(json.load(open('job_scraper/seen_jobs.json'))['seen']))" → 71

4. Archive Old Files

  1. Task 2.5: Archive seen_jobs.json and job_search_tracker.csv

    After confirming all 71 jobs are in the database:

    • mv job_scraper/seen_jobs.json job_scraper/seen_jobs.json.bak
    • mv job_search_tracker.csv job_search_tracker.csv.bak
    • These files remain as safety nets; Phase 1 Sprint 2 will delete them after end-to-end validation
  2. Task 2.6: Add data/ to .gitignore

    Add data/ to .gitignore — the database file contains personal job data and should never be committed.

Verification & Acceptance Criteria

  • python3 db/migrate.py runs without errors and reports: "Migrated 71 jobs successfully, 0 failures"
  • python3 db/client.py stats shows total_jobs: 71
  • Breakdown by status: new: 71, evaluated: 0, skipped: 0, applied: 0
  • Breakdown by fit_rating matches the source JSON distribution
  • Spot-check 5 random jobs: title, company, URL, source, fit_rating match the source JSON
  • FTS5 search for "kubernetes" returns matches (many job descriptions reference Kubernetes)
  • python3 db/client.py scrape-runs list shows the run history from the source JSON
  • seen_jobs.json and job_search_tracker.csv are renamed to .bak
  • data/ is in .gitignore
  • Running migration again (idempotent) detects all URLs already exist (409s) and reports "0 new jobs, 71 already migrated"
