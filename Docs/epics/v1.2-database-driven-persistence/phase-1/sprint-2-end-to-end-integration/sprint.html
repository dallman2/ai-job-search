Sprint 2: End-to-End Integration Test & Cleanup

Phase: 1 Sprint: 2 Depends on: Sprint 1 (Upskill Data Fix)

Objective

Run a full end-to-end integration test of the entire job search pipeline with the database backend: scrape → store → query → evaluate → apply → upskill. Verify every state transition, deduplication behavior, and edge case. After successful validation, finalize the cleanup: delete the archived .bak files, verify .gitignore coverage, and document the new infrastructure in OPENDOC.md. Mark the epic as complete.

Rationale & Context

At this point, all infrastructure is built and all skill files are updated, but no integration test has confirmed that the pieces actually work together. The scraper skill now references db/client.py commands, the upskill skill reads from the database, and the API is running on kind — but a single end-to-end flow will reveal gaps in error handling, missing query parameters, edge cases in the dedup logic, and documentation inconsistencies.

This sprint is deliberately lightweight on code changes. If the previous sprints were done correctly, this sprint is mostly verification with minor fixes. If issues are found, they should be fixed inline and the sprint plan updated.

After verification, the cleanup is irreversible: the archived .bak files are deleted. This is the point of no return — the database is the sole source of truth.

Execution Plan

1. Integration Test: Scrape Flow

  1. Task 5.1: Test "scrape jobs fast" with DB backend

    With the kind cluster and API running:

    1. Verify DB is reachable: python3 db/client.py health → {"status": "ok"}
    2. Record pre-scrape state: python3 db/client.py stats → note total_jobs count
    3. Run "scrape jobs fast" (AI executes scraper skill)
    4. Verify the scraper checks DB health before starting (per updated SKILL.md)
    5. Verify the scraper uses jobs check --dedup-key for pre-filtering
    6. Verify new jobs are inserted via jobs insert
    7. Verify 409 responses for duplicates are handled gracefully (not crash)
    8. Verify run history is logged: python3 db/client.py scrape-runs list --limit 1
    9. Verify post-scrape stats: python3 db/client.py stats → total_jobs has increased (or stayed same if no new jobs)
  2. Task 5.2: Test deduplication across runs

    Run "scrape jobs fast" a second time immediately after the first:

    • All previously seen URLs should return 409 Conflict
    • Only genuinely new jobs (if any) should be inserted
    • The output should report: "X jobs found from Y companies. 0 new since last run."

2. Integration Test: Evaluation & Application Flow

  1. Task 5.3: Test job evaluation flow

    Pick a job from the scrape output (by its database ID):

    1. Load the job: python3 db/client.py jobs get <id> → verify full description_md is present
    2. Run full 5-dimension evaluation (job-application-assistant skill)
    3. After evaluation, update: python3 db/client.py jobs update <id> --status evaluated --evaluation-score 85
    4. Verify: python3 db/client.py jobs get <id> → status is "evaluated", evaluation_score is 85
  2. Task 5.4: Test application tracking flow

    Simulate an application submission:

    1. Generate CV and cover letter (job-application-assistant skill)
    2. After user confirms: python3 db/client.py jobs update <id> --status applied --applied-date "2026-06-09" --notes "CV: applications/company/resume.md, CL: applications/company/cover_letter.md"
    3. Verify: python3 db/client.py jobs get <id> → status is "applied", applied_date and notes are set
    4. Verify: python3 db/client.py jobs list --status applied returns the job
    5. Verify: python3 db/client.py jobs list --status new does NOT return the job (it transitioned out of "new")

3. Integration Test: Upskill Flow

  1. Task 5.5: Test upskill in aggregate mode

    With at least one job in status "evaluated" or "applied":

    1. Run upskill (aggregate mode): the skill should query python3 db/client.py skills aggregate --status applied --status evaluated
    2. Verify the Gap Heatmap has > 0 entries (the evaluated/applied jobs have descriptions with skills)
    3. Verify the Learning Plan has study resources found via WebFetch
    4. Verify the report saves to upskill/report-2026-06-09.md
    5. Verify "Since Last Report" diff works (run twice, second run shows comparison)

4. Edge Case Testing

  1. Task 5.6: Test error scenarios
    ScenarioExpected Behavior
    API unreachable (kind cluster down)Scraper reports "SQLite API not reachable" and aborts gracefully. No partial state.
    Duplicate URL insertReturns 409. Scraper logs "Already tracked" and continues.
    Invalid fit_rating valueAPI returns 422 with field-level validation error. Scraper reports the issue.
    Missing required field (no URL)API returns 422. Scraper reports which job failed and continues.
    Job ID not found on updateAPI returns 404. Scraper reports the error.
    Very long description (> 100KB markdown)TEXT column in SQLite stores up to 1GB. No truncation needed. API handles gracefully.
    FTS5 search with special charactersSQLite FTS5 handles quoting internally. No injection risk.
    Simultaneous scrape runs (not expected but defensive)WAL mode allows concurrent reads and single writer. SQLite serializes writes. No data corruption.

    ## Infrastructure Prerequisites

Before scraping jobs, start the SQLite API on the local kind cluster:

    bash db/start-cluster.sh

Verify the API is reachable:

    python3 db/client.py health

The database file lives at ./data/job-search.db (persisted on the host filesystem
via kind extraMounts). The API is accessible at http://localhost:30080.

To stop the cluster (data persists):

    kind delete cluster --name job-search-local

To restart (data intact):

    bash db/start-cluster.sh
