Epic Overview: v1.2-database-driven-persistence

Epic Vision

Replace the flat-file persistence layer (seen_jobs.json + job_search_tracker.csv) with a SQLite database served via a containerized HTTP API on kind. The current JSON/CSV approach has served 71 tracked jobs well, but it has hit structural limits: no ad-hoc querying, no schema enforcement, two disconnected data silos that can't be joined, and an upskill workflow crippled by reading from an empty CSV while the real data sits in a separate JSON file.

The core directive: unify jobs and applications into a single relational schema, expose it via a simple REST API, and run the whole thing as a kind-deployed Docker container alongside the existing Obscura MCP server. Full-text search via SQLite FTS5, UNIQUE constraints for robust deduplication, and a thin db/client.py CLI that the AI assistant uses instead of raw file I/O.

Success means the user types "scrape jobs fast" and every job lands in a queryable database. The upskill skill analyzes all applied jobs at once. Ad-hoc questions like "show me all high-fit Anthropic jobs" are a single API call, not a Python dictionary scan.

Key Design Decisions

DecisionRationale
SQLite, not PostgreSQLZero-dependency (Python stdlib). File-based, single-user, no server process. Perfect fit for < 1000 records.
FastAPI HTTP wrapper, not raw sqlite3SQLite has no network protocol. The API wrapper makes it a "database container" that the AI can query via curl or urllib from any process.
kind, not docker-composeUser preference; matches work infrastructure patterns. kind gives us PersistentVolumes, health probes, and declarative manifests without a separate orchestrator.
Obscura stays as docker runObscura uses stdio transport for MCP. Moving it to kind would break stdin/stdout communication. Only the database moves to kind.
HostPath via extraMountsThe DB file lives on the Mac filesystem (./data/job-search.db), surviving kind cluster teardown. Standard macOS backup covers it.
FTS5 for full-text searchBuilt into SQLite. Triggers keep the index in sync automatically. Enables queries like "kubernetes AND agentic" against job descriptions.
evaluation_score column (0-100)Separate from fit_rating (enum). The scraper's rapid score sets fit_rating. The full 5-dimension evaluation sets evaluation_score. Upskill uses evaluation_score for weighted gap analysis.

Conventions

  1. The SQLite database file is stored at ./data/job-search.db on the Mac host filesystem, not inside the container's ephemeral filesystem
  2. All API communication goes through db/client.py — the AI assistant never calls curl directly or uses raw sqlite3
  3. The db/client.py CLI uses only Python stdlib (urllib.request, json) — zero pip dependencies
  4. Schema migrations are additive (ALTER TABLE ADD COLUMN); the API auto-runs schema.sql on first start if the DB file is absent
  5. seen_jobs.json and job_search_tracker.csv are archived (renamed to .bak), not deleted, until Phase 1 Sprint 2 confirms the migration
  6. data/ is added to .gitignore — job data is personal and should never be committed
  7. AI tooling references in generated CVs/cover letters continue to reference "opencode" by name (v1.0 convention, unchanged)
  8. The kind cluster name is job-search-local; the namespace is job-search; the service is sqlite-api

Risk Registry

IDRiskLikelihoodImpactMitigation
R1 kind cluster deleted → DB lost Medium High extraMounts maps ./data/ to the kind node; DB file lives on Mac filesystem. Cluster teardown does not delete it.
R2 FTS5 content sync drift Low Medium AFTER INSERT/UPDATE/DELETE triggers keep FTS index in lockstep with the jobs table. Standard SQLite pattern, well-tested.
R3 API container not running during scrape Medium High Scraper skill checks python3 db/client.py health before starting. If unreachable, reports the issue and aborts with instructions to start the cluster.
R4 Docker image build takes too long / fails on Mac Low Medium Minimal Dockerfile: python:3.12-slim base, two pip packages, one COPY. Build time < 30 seconds on first build.
R5 Kind cluster port conflicts with existing services Low Low NodePort 30080 is a non-standard port. Verified no conflicts with existing containers (8080, 3000, 5432, 6379 in use by work projects).
R6 Migration script corrupts or loses data Low High seen_jobs.json is archived (not deleted) before migration. Migration is additive. Row count and spot-checks are verified post-migration.

Epic Acceptance Criteria

  • python3 db/client.py health returns {"status": "ok"} when the kind cluster is running
  • All 71 jobs from seen_jobs.json are queryable via python3 db/client.py jobs list
  • python3 db/client.py jobs search --q "kubernetes agentic" returns FTS5 matches across title, company, and description
  • Inserting a job with a duplicate URL returns HTTP 409 and a clear error message
  • "scrape jobs fast" runs without referencing seen_jobs.json or job_search_tracker.csv
  • New scraped jobs appear in the database with correct fields and can be queried immediately
  • Evaluating a job (status: new → evaluated) updates the database and persists across scraper runs
  • Marking a job as applied (status: applied) sets applied_date and notes in a single UPDATE
  • python3 db/client.py stats returns accurate aggregate counts by status, fit_rating, source, and company
  • The upskill skill successfully queries applied jobs and produces a gap heatmap (not an empty report)
  • The kind cluster can be torn down and recreated without data loss (DB file on ./data/)
  • No regressions in CV/cover letter generation or interview prep (job-application-assistant unchanged)
