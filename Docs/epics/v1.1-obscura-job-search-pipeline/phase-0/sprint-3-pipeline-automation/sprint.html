Sprint 3: Pipeline Automation & Polish

Phase: 0 Sprint: 3 Depends on: Sprint 2

Objective

Wire the full pipeline into single-command workflows ("scrape jobs fast", "scrape jobs deep", "scrape jobs new"). Add error resilience so individual board failures do not crash the batch. Add run state tracking so "new" mode can diff against the last run. Polish output formatting. At the end of this sprint, the entire pipeline is production-grade: one command runs the full search→extract→score flow, and the user gets clean, actionable results even when some boards are down.

Rationale & Context

Sprint 2 produces a working scraper + evaluation chain. But the pipeline breaks if any single board is unreachable. Greenhouse has occasional Cloudflare mode changes. Wellfound deploys on Fridays and sometimes breaks pagination. Ashby goes down for maintenance. The LLM should not stop and report "Wellfound returned a 502, exiting." It should skip the broken board, continue with the rest, and report what failed.

Additionally, the user needs to know what changed since last time. "scrape jobs new" compares the current run against the last_run timestamp in seen_jobs.json and presents only jobs first seen after that timestamp. This is the mode they will use most often.

Output polish matters: no raw JSON dumped at the user, no internal state leaked. A clean summary line ("Found 23 jobs, 8 new since last run, 6 high matches") followed by the ranked table.

Scope

In-Scope

  • Implement "scrape jobs fast" as a single-command pipeline (priority 1-3 queries)
  • Implement "scrape jobs deep" (all 5 priority tiers)
  • Implement "scrape jobs new" (diff against last_run timestamp)
  • Error resilience: per-board error handling, retry once on timeout, skip and report on persistent failure
  • Run state tracking: last_run timestamp, run_history array in seen_jobs.json
  • Output polish: summary line, clean table, no raw JSON, no internal state leaked
  • Docker health check: if the Obscura container is not running, report how to start it and exit gracefully

Out-of-Scope

  • GitHub Actions scheduled runs (future work, referenced as optional)
  • Slack/email notifications
  • Dashboard or web UI
  • Proxy rotation or IP management (stealth mode handles anti-bot for v1.1)
  • Cookie/session management for authenticated boards

Execution Plan

1. Implement Pipeline Modes

  1. Task 3.1: Add "fast" and "deep" mode triggers to SKILL.md

    Update the skill's trigger logic: detect "fast" (or absence of "deep") → run priority 1-3 queries. Detect "deep" → run all 5 priority tiers. Detect "new" → run the selected tier and diff against last_run. If neither "fast" nor "deep" is specified, default to "fast."

    The search phase should describe running queries in order by priority tier, collecting results across all boards before moving to deduplication. Parallel execution where the board supports it (e.g., Google queries can run concurrently with board-specific searches).

  2. Task 3.2: Add "new" mode diff logic to SKILL.md

    When "new" mode is triggered: load last_run from seen_jobs.json. After fetching and deduplicating, filter the results to only include entries with first_seen after last_run. Present only those entries. Update last_run to the current timestamp after the run completes.

2. Add Error Resilience

  1. Task 3.3: Document error handling strategy in SKILL.md

    Add an error handling section to the skill's constraints:

    Obscura container down
    Report: "Obscura container is not running. Start it with: docker start obscura." Exit the scrape. Do not attempt any board access.
    Individual URL timeout
    Retry once. If it fails again, skip the URL and continue. Report the skipped URL at the end.
    Board unreachable (HTTP 5xx, DNS failure)
    Skip the entire board. Continue with remaining boards. Report: "[Board name] could not be reached: [error]. Continuing with other boards."
    Rate limiting (HTTP 429)
    Wait for the Retry-After header value (or default 60s). Retry once. If still rate-limited, skip the board.
    Empty or partial results
    If a board returns results but they seem incomplete (fewer than expected, missing fields), flag the board as "partial results" and note it in the output.

3. Implement Run State Tracking

  1. Task 3.4: Extend seen_jobs.json schema for run history

    After each scrape run, update seen_jobs.json:

    {
  "seen": { ... },
  "last_run": "2026-06-08T14:30:00Z",
  "run_history": [
    {
      "date": "2026-06-08T14:30:00Z",
      "mode": "fast",
      "queries_run": 15,
      "jobs_found": 23,
      "jobs_new": 8,
      "boards_failed": ["wellfound"]
    }
  ]
}

    The run_history array grows over time. Purging old entries is not required for v1.1 (the array stays small with on-demand runs).

4. Polish Output Format

  1. Task 3.5: Define output polish standards in SKILL.md
    • Always open with a summary line: "Found [total] jobs, [new] new since last run, [high] high matches, [med] medium matches. [skipped] low matches skipped."
    • The ranked table uses clickable markdown links: [Company](url) for the company column.
    • Fit badges: HIGH, MED, LOW in the Key Match column.
    • Never show raw JSON, internal state, or tool call results.
    • If any boards failed, append a brief "Issues" section at the bottom: "[Board] could not be reached. [Board] returned partial results."
    • If no new jobs were found: "No new jobs found since [last_run date]. Try 'scrape jobs deep' for a broader search."

5. Future: GitHub Actions (Documented, Not Implemented)

  1. Task 3.6: Document future scheduled run option in SKILL.md

    Add a brief note at the end of the skill describing how scheduled runs would work in the future: a weekly GitHub Actions cron that runs "scrape jobs new" and posts results as an issue comment. Mark as "future work, not implemented in v1.1."

Verification & Acceptance Criteria

  • "scrape jobs fast" runs priority 1-3 queries end-to-end without manual intervention
  • "scrape jobs deep" runs all 5 priority tiers
  • "scrape jobs new" returns only jobs first seen after the last_run timestamp
  • If Obscura container is stopped, the scrape reports "docker start obscura" and exits
  • If one board fails (e.g., 502 from Wellfound), the scrape continues with remaining boards and reports the failure
  • Output opens with a summary line: counts of total, new, high, medium, skipped jobs
  • Output contains no raw JSON, no internal state, no tool call results
  • seen_jobs.json is updated with last_run timestamp and appends to run_history after each scrape
  • If no new jobs found, output suggests "scrape jobs deep" as next step
  • Fit badges are consistently formatted: HIGH, MED, LOW
