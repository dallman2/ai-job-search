Sprint 1: Scraper Skill Rewrite

Phase: 0 Sprint: 1 Depends on: Sprint 0

Objective

Rewrite the job-scraper SKILL.md from its current Danish-focused, CLI-tool-based design into an SF-targeted, Obscura-powered skill that can autonomously search job boards, extract listings, deduplicate against previously seen jobs, rapid-score candidates, and present ranked results. Create the tracking infrastructure (seen_jobs.json, job_search_tracker.csv). Document board-specific extraction patterns. At the end of this sprint, "scrape jobs fast" returns deduplicated, rapid-scored job listings from live boards.

Rationale & Context

The current job-scraper/SKILL.md was written for a Danish job market context. It references CLI tools (jobindex-search, jobbank-search, jobnet-search, jobdanmark-search) that search Danish job boards. It assumes geographic filters for Copenhagen, Sjælland, and Hovedstaden. None of this applies to the candidate's actual profile: San Francisco Bay Area, targeting frontier AI labs and AI-native infrastructure companies at Senior+ level.

The rewrite must keep the same skill structure (goal-oriented purpose, constraints, state management, search/process/output phases) but replace every Danish-specific reference with SF AI context. The CLI tools are replaced by Obscura MCP tools. The search scope shifts from Danish job portals to Greenhouse, Ashby, Wellfound, YC Jobs, and Google→LinkedIn.

Obscura provides roughly 12 MCP tools. The key ones for scraping are browser_navigate (navigate to a URL, with optional waitUntil for dynamic content), browser_snapshot (return current page URL, title, and body text), and browser_evaluate (execute arbitrary JavaScript). For pagination and interaction: browser_click, browser_wait_for. The skill should describe what to do (navigate to search results, extract listing URLs) without prescribing exactly how to do it — the LLM reasons about tool selection dynamically.

Deduplication uses two data stores: seen_jobs.json (all jobs ever fetched, keyed by URL or company+title, with status: new/skipped/evaluated/applied) and job_search_tracker.csv (a log of actually-applied jobs). Both must be created with empty initial states.

Execution Plan

1. Create Tracking Infrastructure

  1. Task 1.1: Create seen_jobs.json

    Create job_scraper/seen_jobs.json with initial state. Schema: {"seen": {}} (empty object, keys are compound dedup keys). last_run field: null initially, updated to ISO timestamp after each scrape run. Each seen entry: {title, company, url, first_seen, status, fit_rating}.

  2. Task 1.2: Create job_search_tracker.csv

    Create job_search_tracker.csv with header row: company,role,date_applied,status,notes. Empty initially. Rows are appended when the user confirms an application was submitted.

2. Document Per-Board Extraction Patterns

  1. Task 1.3: Add extraction patterns to SKILL.md

    Document the following patterns in the skill's search phase section:

    Greenhouse
    Job board pages at /jobs. Detail pages at /jobs/[id]. Use browser_navigate to the job board URL, browser_snapshot to extract listing titles and URLs, then browser_navigate to each detail page for full descriptions. Extraction: page <h1> for title, .location for location, main content area for body.
    Ashby
    Job board pages at /[company]. Detail pages at /[company]/[id]. JS-rendered; requires waitUntil: "networkidle0". Extraction: page title for role, structured data blocks for requirements.
    Wellfound
    Search results load dynamically via infinite scroll. Use browser_wait_for with selector: ".job-listing". May need browser_evaluate to scroll for more results. Detail pages at /jobs/[id].
    YC Jobs
    Standard pagination at /jobs?tags=ai&page=N. Listing cards contain title, company, description snippets. Filter by tags: ai, ml, infrastructure.
    Google → LinkedIn
    Google search queries (site:linkedin.com/jobs "senior engineer" [keywords] San Francisco) return public LinkedIn job posting URLs. Navigate to the URL via Obscura for the full description. For companies without Greenhouse/Ashby (OpenAI, Anthropic), Google search their career pages directly.

3. Rewrite SKILL.md

  1. Task 1.4: Rewrite the skill's purpose, constraints, and state section

    Update the YAML frontmatter: name stays job-scraper, description updated to mention SF, AI jobs, Obscura-powered. Change triggers to: job scrape, find jobs, search jobs, new jobs, job search, scrape jobs.

    Update Purpose: "Your purpose is to search San Francisco Bay Area job boards for AI/ML engineering positions at Senior+ level, using Obscura MCP tools for browser automation. Deduplicate against previously seen jobs. Rapid-score and present ranked results."

    State section: load search-queries.md for the configured search strategy. Load job_scraper/seen_jobs.json and job_search_tracker.csv. Recognize "fast" (priority 1-3) vs "deep" (all 5) vs "new" (diff against last_run) modes.

  2. Task 1.5: Rewrite the Search phase

    Replace "Use the job portal CLI tools" with Obscura-based search. For Google-based queries: execute the search in Obscura by navigating to the Google search URL. For board-specific searches: navigate to the board's search endpoint. Extract listing URLs from result pages. Use parallel Obscura tool calls where the board supports it.

    Pre-filter logic: extract title and company from search snippets. Skip if: below Senior level, requires relocation outside SF Bay Area, company+title already in seen_jobs.json, company+role in job_search_tracker.csv.

  3. Task 1.6: Rewrite the Fetch & Deduplicate phase

    For each promising result, navigate to the detail page via Obscura. Extract: title, company, location, posting date, full description (as markdown), application deadline (if listed). Skip any URL or company+title combo already in seen_jobs.json. Skip any company+role already in job_search_tracker.csv. Skip jobs with expired deadlines. Skip jobs outside commute range (San Jose is borderline, flag it).

    After fetching, add ALL jobs to seen_jobs.json with title, company, URL, first_seen date, fit rating, and status. Only present jobs with status new.

  4. Task 1.7: Rewrite the Fit Assessment phase (rapid scoring)

    Replace the existing rapid signal with SF AI context scoring:

    High match
    Primary skills directly involved (TypeScript, Python, Kubernetes, MCP, agentic systems, AI/ML engineering). Senior+ level. SF or remote-acceptable. Role type matches target (infrastructure, platform, agentic, frontier models, voice/multimodal).
    Medium match
    Secondary skills match (React, Node.js, Docker, AWS, CI/CD, adversarial ML). Senior level but adjacent role type (full-stack product, SRE, data engineering).
    Low match
    No skill match OR below Senior level OR requires relocation OR deal-breaker (dedicated people management, heavily process-driven). Skip these before fetching detail pages.
  5. Task 1.8: Rewrite the Output phase

    Present new jobs in a table sorted by fit (high first): Fit, Title, Company, Location, Key Match Signals, URL. For each high-match job, add 2-3 bullets: why it matches, key requirements, any red flags. After presenting: "Want me to evaluate any of these in detail? Just give me the number(s)." If user picks a number, defer to Sprint 2's evaluation handoff logic.

  6. Task 1.9: Add Google search queries to search-queries.md

    Add Priority 4 section: LinkedIn via Google. Queries capture public LinkedIn postings for companies that don't use Greenhouse/Ashby. Include direct career page searches for frontier AI labs (OpenAI, Anthropic, Mistral, xAI).
