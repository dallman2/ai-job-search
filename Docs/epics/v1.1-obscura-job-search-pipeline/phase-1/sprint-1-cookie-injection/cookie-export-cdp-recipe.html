Cookie Export via Chrome DevTools Protocol

Type: Sprint 1 Corollary Parent: Sprint 1: Cookie Injection & Authenticated Boards Status: completed

Problem

The job-scraper pipeline needs the candidate's live browser session cookies to search LinkedIn and Wellfound. Obscura's browser_set_cookie tool can inject cookies before navigation — but the cookies must first be extracted from the candidate's real browser, where they are already signed in.

Constraints:

  • No browser extensions. Extensions that read all cookies (e.g., EditThisCookie) are a security vulnerability — they can exfiltrate session tokens to third parties.
  • No Keychain access. Reading Chrome's encrypted SQLite cookie database requires decrypting with the macOS Keychain-derived key. This means granting the terminal Keychain access, which injects trust into a broad attack surface.
  • Must capture httpOnly cookies. LinkedIn's session token (li_at) is httpOnly — inaccessible via document.cookie from JavaScript in the page context.
  • No pip dependencies. The candidate's system Python may not have pycryptodome, cryptography, or websocket-client installed.
  • Must be a script we own. The solution must be a file in the repository, not a third-party tool or manual process.

Solution: Chrome DevTools Protocol (CDP)

Chrome exposes a debugging interface on localhost:9222 when started with --remote-debugging-port=9222 --user-data-dir=/tmp/chrome-cdp-session. This is the same protocol that DevTools, Puppeteer, and Playwright use internally. The Network.getCookies CDP method returns all cookies for a domain including httpOnly — because it runs at the browser engine level, not in the page's JavaScript sandbox.

Architecture

Chrome (--remote-debugging-port=9222 --user-data-dir=/tmp/chrome-cdp-session)
  │
  ├── TCP endpoint: http://localhost:9222/json
  │   Returns JSON array of open tabs with WebSocket debugger URLs
  │
  ├── WebSocket: ws://localhost:9222/devtools/page/[id]
  │   Bidirectional CDP command channel
  │
  └── CDP Command: Network.getCookies
      Returns ALL cookies for matching domains (including httpOnly)

export_chrome_cdp.py
  │
  ├── 1. GET /json → discover tabs, find matching domain
  ├── 2. WebSocket connect to tab's debugger URL
  ├── 3. Send {method: "Network.getCookies", params: {urls: [...]}}
  ├── 4. Receive response, filter by domain, format as JSON
  └── 5. Output to stdout (piped to cookies/linkedin.json)

Implementation

The script at cookies/export_chrome_cdp.py uses only Python standard library:

  • urllib.request — HTTP GET to localhost:9222/json for tab discovery
  • socket + ssl — TCP+TLS connection with WebSocket upgrade handshake, frame encoding/decoding
  • json — CDP command serialization and response parsing
  • base64, hashlib, os — WebSocket handshake key generation (Sec-WebSocket-Key)
  • struct — WebSocket frame length encoding

Optimization: If websocket-client is available in the Python environment, the script uses it for cleaner WebSocket handling and falls back to the stdlib implementation otherwise. The websocket-client path is < 20 lines; the stdlib path is ~80 lines of minimal WebSocket client.

WebSocket handling (stdlib fallback): The script implements a minimal RFC 6455 client — unidirectional text frames only (send text, receive text, detect close). No ping/pong, no fragmentation, no extensions. This is sufficient for the single CDP command/response exchange used here.

Usage

Step 1: Start Chrome with Remote Debugging

Fully quit Chrome (Cmd+Q). Then launch with a temp profile — Chrome 149+ requires --user-data-dir pointing to a non-default directory for security:

/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome \
  --remote-debugging-port=9222 \
  --user-data-dir=/tmp/chrome-cdp-session \
  --remote-allow-origins='*'

This launches a separate Chrome window with a fresh profile. Your main Chrome windows are untouched. The temp profile at /tmp/chrome-cdp-session/ stores session data for this debug instance only — delete it when you're done.

Why three flags:

  • --remote-debugging-port=9222 — enables the CDP HTTP/WebSocket server.
  • --user-data-dir=/tmp/chrome-cdp-session — Chrome 149+ refuses to enable debugging on the default profile ("DevTools remote debugging requires a non-default data directory").
  • --remote-allow-origins='*' — Chrome 149+ validates the WebSocket Origin header. Without this, the script's connection is rejected with HTTP 403 ("Rejected an incoming WebSocket connection from the http://localhost:9222 origin").

Verify the port is open before proceeding:

curl -s http://localhost:9222/json | python3 -c "import sys,json; print(f'{len(json.load(sys.stdin))} tabs open')"

Step 2: Sign In to Target Sites

Navigate to each site you want to extract cookies from and sign in:

  • linkedin.com — sign in, verify you can see your feed or jobs page
  • wellfound.com — sign in, verify you can browse job listings

Step 3: Run the Export Script

cd .opencode/skills/job-scraper
python3 cookies/export_chrome_cdp.py linkedin.com > cookies/linkedin.json
python3 cookies/export_chrome_cdp.py wellfound.com > cookies/wellfound.json

Step 4: Verify Output

head -5 cookies/linkedin.json
# Should show JSON array with li_at, JSESSIONID, etc.

python3 -c "import json; d=json.load(open('cookies/linkedin.json')); print(f'{len(d)} cookies, httpOnly: {sum(1 for c in d if c[\"httpOnly\"])}')"
# Should show httpOnly count > 0 (li_at is httpOnly)

Step 5: Resume Normal Chrome

Close Chrome and reopen normally (without the --remote-debugging-port flag). Cookies are now stored in cookies/ and ready for the scraper pipeline.

Security Analysis

Edge Cases & Troubleshooting

Port not open — "requires a non-default data directory" (Chrome 149+)
This is the definitive diagnostic for Chrome 149+ on macOS. Chrome prints this message to the terminal on launch and silently refuses to bind the debug port. The fix is --user-data-dir=/tmp/chrome-cdp-session. Run diagnostics: 
# Check if port is bound
curl -s http://localhost:9222/json
# If "Connection refused" and Chrome printed the warning above:
# restart with --user-data-dir=/tmp/chrome-cdp-session
Chrome already running (session conflict)
The debug port and temp profile must be specified at Chrome launch time. If Chrome is already open, Cmd+Q to fully quit, then launch with both flags. The temp profile window is independent — your main Chrome profile is not affected.
Port conflict with another process
If port 9222 is in use by another process, change the port: --remote-debugging-port=9223 and pass --port=9223 to the script. The script currently defaults to port 9222.
No tabs match the domain
The script searches open tabs for a URL containing the target domain. If no tab is on linkedin.com, the script uses the first available tab but the Network.getCookies response may be incomplete. Open a tab to the target site before running the script.
Empty cookie output
Verify you are signed in to the site in that Chrome session. CDP reads live cookies from the browser process — if you signed in on a different Chrome profile or before restarting with the debug flag, the session may not be active.
WebSocket handshake failure
Ensure Chrome was started with --remote-debugging-port=9222 (not a different port). Verify with curl http://localhost:9222/json — should return a JSON array of tabs.
Script syntax warning
The script uses r"""...""" raw docstrings to avoid Python escape sequence warnings on filesystem paths containing backslashes.

Future Considerations

  • Transport evaluation history: During Sprint 1 we evaluated four CDP transport approaches on Chrome 149 macOS: TCP with --remote-debugging-address (failed — port not bound on default profile), Unix domain sockets via --remote-debugging-socket-name (failed — requires --headless), --remote-debugging-pipe subprocess mode (rejected — ties Chrome lifecycle to Python process), and TCP with --user-data-dir temp profile (accepted — the only combination that works on Chrome 149).
  • Temp profile cleanup: The script doesn't manage the temp profile. Delete /tmp/chrome-cdp-session/ manually after use. Future versions could auto-delete on script exit.
  • Multi-profile support: The script currently connects to whatever Chrome instance is running on port 9222. If the candidate uses multiple Chrome profiles, the script can be extended to enumerate profiles via /json/list.
  • Firefox support: Firefox also supports CDP via --remote-debugging-port. The same script works with Firefox if it exposes the CDP-compatible endpoint. This is not yet tested.
  • Cookie refresh automation: In the future, a scheduled GitHub Actions workflow could prompt the candidate to refresh cookies via a reminder, but automatic refresh is not possible without stored credentials (which we deliberately avoid).
  • WebSocket keep-alive: If multiple CDP commands are needed in future scripts, ping/pong frame handling should be added to the stdlib WebSocket implementation.
